# Система отслеживания камней в кёрлинге и сопоставления пиксельных координат с реальным полем

## 1. Архитектура системы

Система состоит из двух ключевых компонентов:

- Модель детекции ключевых точек поля (дома кёрлинга) — реализована на основе YOLOv11, обучена на ббоксах, соответствующих 12 точкам игрового поля.
- Модель детекции камней кёрлинга — также реализована на YOLOv11, предназначена для обнаружения камней в кадре.

Для отслеживания камней во времени используется трекер DeepOCSORT, расширенный возможностью ReID (повторной идентификации). Координаты детектированных камней преобразуются из пиксельного пространства в физические координаты (сантиметры) при помощи гомографии, вычисленной по 12 точкам, соответствующим известной геометрии кёрлингового поля.

Визуализация результатов включает:
- Аннотированные bounding boxes с ID треков,
- Отображение траекторий движения камней,
- Подписи с реальными координатами в сантиметрах.

---

## 2. Сбор и аннотация данных

### Источники данных

В работе использовались как публичные датасеты с платформы Roboflow, так и самостоятельно размеченные данные:
- Основной датасет для камней: Curling-Detection — содержит 1239–3369 изображений с разметкой камней кёрлинга.
- Для разметки поля был собран датасет, представляющий собой фотографии поля для керлинга с разных ракурсов.

### Аннотации

Хотя задача формально относится к классу keypoint detection, было принято решение переформулировать её как object detection:
- Вместо разметки отдельных точек (keypoints) аннотировались ограничивающие рамки (bounding boxes) вокруг каждой из 12 характерных точек поля (центры домов, линии, углы).
- На этапе инференса координаты ключевых точек извлекаются как центры bounding box’ов.

Были протестированы три варианта количества точек: 4, 12 и 22. Экспериментально установлено, что 12 точек обеспечивают оптимальный баланс между устойчивостью гомографии и простотой разметки.

## 3. Процесс обучения моделей

Для обеих задач (камни и ключевые точки поля) использовались архитектуры YOLOv11:
- YOLOv11s (small) — для более быстрого инференса и меньшего потребления памяти,
- YOLOv11m (medium) — для максимальной точности.

Модели обучались с использованием стандартных конфигураций Ultralytics с адаптацией под специфику задач:
- Для детекции камней использовался порог уверенности conf=0.7 на инференсе.
- Для ключевых точек поля — top-k=10 детекций с наибольшей уверенностью отбирались для вычисления гомографии. (количество точек для гомографии можно уменьшить/увеличить)

Использовалась аугментация данных (шум, размытие), чтобы повысить робастность моделей к различным условиям освещения и ракурсам съёмки.

## 4. Пайплайн обработки видео

### 4.1. Инициализация

При создании экземпляра CurlingDemoPipeline:
- Загружаются две предобученные модели YOLO на GPU (если доступен),
- Инициализируется трекер DeepOCSORT с параметрами:
  - det_thresh=0.6 — порог детекции для трекера,
  - max_age=60 — максимальное количество кадров без появления объекта до его "смерти".

### 4.2. Вычисление гомографии

- Гомография вычисляется по первому кадру видео:
  1. Модель ключевых точек детектирует bounding boxes.
  2. Центры box’ов интерпретируются как изображения физических точек.
  3. Используя известные физические координаты (в сантиметрах), вызывается cv2.findHomography.

### 4.3. Обработка каждого кадра

Для каждого кадра выполняется следующая последовательность:
1. Детекция камней с помощью stone_detection_model.
2. Трекинг через DeepOCSORT, который возвращает ID, координаты и уверенность.
3. Преобразование центров камней в реальные координаты с помощью предварительно вычисленной гомографии.
4. Визуализация:
   - Рисуются bounding boxes и ID.
   - Подписываются координаты в сантиметрах.
   - Накапливается и отрисовывается траектория движения (если камень находится внутри игрового поля, y < 823 см).

### 4.4. Ограничения и особенности

- Статичное поле: предполагается, что камера не движется и гомография не меняется во времени.
- Центр как keypoint: использование центров bounding box’ов вместо настоящих ключевых точек может снижать точность при большом перекосе или несимметричной перспективе.
- Отказ от ReID: если веса osnet_x1_0.pt отсутствуют, трекер работает без повторной идентификации (ID могут переприсваиваться после исчезновения объекта).
